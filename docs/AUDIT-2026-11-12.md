# Tagkin: audit before batch 2 (12 Nov 2026)

Scope: everything done so far (steps 1 to 6 and batch 1 of step 7): brief, rules, system logic, tech design, ADRs, backlog, prototypes, Sprint 0 plan, monorepo. Question: what is missing, and where does it hurt if it isn't fixed now?

Priorities say **when** each finding must be settled, because that is when leaving it costs the most:

- **P0, before batch 2 is merged:** it shapes code that is about to be written.
- **P1, before batches 3 and 4:** data model, auth, environments.
- **P2, before M1 goes public:** live finder pages.
- **P3, before M2 sells:** money, products, law.
- **P4, before the stores.**
- **P5, ideas:** worth having, but nothing breaks without them.

Owner: **S** is a decision or action for Selasey, **C** is build work for Claude, **X** needs an outside expert (tax advisor or lawyer).

**Decided 12 Nov:** A1 to A3 (rule 4.1), B1 to B8 and F1 (ADR 0013, 0014), B16, finder phone replies (later). Open decisions: 2, 4 to 9 below.

## A. Product rules and data

| ID | Finding | Where it hurts | Fix | When | Who |
|---|---|---|---|---|---|
| A1 | **The code and QR format isn't frozen.** The QR holds a URL whose path can never change once printed. | Every printed tag breaks if the route or domain changes. | Freeze it in the rules: `https://tagkin.app/TK-XXXX-XXXX` (or the shorter `tagkin.app/XXXXXXXX`), encoded in upper case. Upper case lets the QR use its compact alphanumeric mode: a smaller grid that scans better on small tags. | P0 | S decides, C applies |
| A2 | **No check character in codes.** Finders type codes by hand (TK-11). | A typo goes to a lookup that fails; guessed codes cost lookups. | Add one check character (Luhn mod 31 over the alphabet). The page can then say "check the code" before any lookup, and guessing gets much harder. Decide before the seed data (S0-6). | P0 | S, C |
| A3 | **Random codes can spell words.** The alphabet still has F, U, C and K. | A rude word printed on a gift tag. | A blocklist checked when codes are generated, with a test. | P0 | C |
| A4 | **Money and tax fields are missing:** no VAT rate or amount, no country of supply, no invoice number, no integer cents. | Wrong VAT under the EU One-Stop Shop (OSS) rules; invoices that don't meet the legal requirements. | Order fields: `amount_cents`, `vat_rate`, `vat_cents`, `country`, `invoice_no`. Use Stripe Tax or a fixed rate once the tax advisor has confirmed. | P1 | C, X |
| A5 | **One partner order per order.** The data model has a single `partner_order_id` and `tracking_url`. | Two partners (A7) means two parcels, two tracking numbers and two stage timelines. | A **Shipment** entity: order items belong to a shipment, and each shipment has a partner, tracking and stage. The order shows the slowest stage. | P1 | C |
| A6 | **No print-file pipeline.** Every tag needs its own vector QR, code text, label, colour, bleed and print colour profile, generated per order and sent to the partner. | TK-53 can't be built. Proofs may not match the preview. | A server function produces print-ready PDF or SVG from the same renderer as the preview, stores it, and passes its link to the partner. Add it as a story in M2. | P1 | C |
| A7 | **The product range assumes one print-on-demand partner.** Engraved QR on metal pet tags, PVC luggage labels, gift cards with a printed PIN and scratch-panel packs aren't standard print-on-demand products. | Shapes we can't deliver; M4 gifting is blocked. | Make the samples decide the range. Keep the fulfilment adapter able to use several partners. Use a mailer insert for the PIN, or put the PIN only in the email. | P1 | S |
| A8 | **No unit economics.** Prices are samples, with no model of partner cost, shipping, Stripe fees, VAT, translation and SMS costs, the first-tag discount or free shipping over €15. | Selling at a loss, especially small orders and pet tags. | A one-page cost model per product, built from the sample quotes. | P3 | S, C |
| A9 | **QR size on the smallest tags.** A 25 mm pet disc gives a QR of about 13 mm, on curved metal. | It won't scan reliably, which breaks the core promise. | Set a minimum QR size per product (about 15 mm for close scanning) and error-correction level M or Q; test with samples on 3 phones. Drop size S if it fails. | P1 | S, C |
| A10 | **Withdrawal right for blank, gift and shop tags.** The "made to order" exception may not cover tags without a personal design. | Refund claims; terms that can't be enforced. | Lawyer check. Personalised orders keep the exception; blank tags may need the 14-day right and the model withdrawal form. | P3 | X |
| A11 | **Domain permanence.** Printed codes rely on tagkin.app forever. | A lapsed domain kills every tag, and with it trust in the product. | Renew for the maximum term (up to 10 years for .app) once revenue starts, and write a continuity promise in the terms. | P3 | S |

## B. Architecture and technical choices

| ID | Finding | Where it hurts | Fix | When |
|---|---|---|---|---|
| B1 | **No translation library.** TK-92 says all text is externalised from day one, but nothing is chosen. | Hard-coded English strings that are costly to retrofit. | **i18next** in `packages/i18n` (works in Next.js and React Native), with messages in shared JSON. Starts with batch 2. | P0 |
| B2 | **No styling or theme approach.** The tokens package has no output format yet. | Dark mode and tokens done twice, drifting. | Tokens generated into CSS variables (web) and a typed object (mobile), plus a small theme hook for light, dark and system. No heavy UI kit. | P0 |
| B3 | **No navigation or deep-link plan.** The blank template has no router. Activation links and report links should open the app through universal links (`https://tagkin.app/...`), not only `tagkin://`. | Links open the website instead of the app; the `.well-known` routes clash with the code routes. | **Expo Router**. Reserve `/.well-known/apple-app-site-association` and `assetlinks.json` in the web app. Set `associatedDomains` and `intentFilters` now. | P0 |
| B4 | **Forms and data fetching aren't chosen.** | Each screen does validation and caching its own way. | react-hook-form with the shared Zod schemas, and TanStack Query on both platforms. | P0 |
| B5 | **No test stack.** The Definition of Done says "tests for the logic", but no tools are named. | CI with nothing proper to run; access-control (RLS) bugs go unseen. | Vitest (units); pgTAP via `supabase test db` (access rules and state machines); Playwright with an accessibility checker (web journeys, finder flow); Maestro (mobile, later). | P0 |
| B6 | **No migration or release practice.** | A dashboard edit drifts from the code; a deploy runs before its migration; a breaking column change takes the app down. | Migrations only through CI (staging, then production after approval). Changes in two steps: add the new structure, switch over, remove the old. Migrate first, then deploy. Never edit production from the dashboard. | P0 |
| B7 | **No app update policy.** | Old app versions call new APIs. | EAS Update with channels (preview, production); runtime version from the native fingerprint; a minimum supported version check. Decide before the first EAS build (S0-9). | P1 |
| B8 | **No environment check.** S0-11 adds keys, but nothing validates them. | A missing key fails at runtime in production. | A Zod-checked env file per app that fails at build time. Public and secret keys are kept apart. | P1 |
| B9 | **Live replies for anonymous finders aren't designed.** Supabase Realtime needs a JWT, and finders have no account. | The core finder thank-you page (TK-16) stalls in M1. | Supabase anonymous sign-in, or a JWT signed by the server and scoped to the report token, with access rules keyed on it. Decide in batch 3. | P1 |
| B10 | **Rate-limit store not chosen** (Upstash in the EU, or Postgres). | Code guessing and spam on day one. | Postgres counters at launch (one fewer provider); revisit when traffic grows. | P1 |
| B11 | **No bot protection** on sign-in code requests and finder reports. | Email bombing through the sign-in form (it costs Brevo quota and reputation); spam reports. | Cloudflare Turnstile, which Supabase Auth supports for captchas; invisible to people. | P1 |
| B12 | **Finder pages aren't marked "noindex".** | Owner messages and photos appear in Google. | `X-Robots-Tag: noindex`, no codes in the sitemap, plus security headers and a content security policy. | P2 |
| B13 | **Scan counting is naive.** Link previewers, security scanners and crawlers can hit `/TK-…`. | False "scanned" alerts in Lost mode, which worry owners. | Count a scan only from a real page load (a small client beacon), and filter known bots. | P2 |
| B14 | **Expo's push service is US-based**, and push text includes item names. | Personal data leaves the EU, against the EU-only stance in ADR 0012 and system logic section 10. | Neutral push text ("Someone found one of your tags"), with details only in the app; or send directly to APNs and FCM. Record the decision in ADR 0009. | P1 |
| B15 | **City from IP is imprecise on mobile networks.** | "Scanned near Frankfurt" when the item is in Darmstadt. | Use Vercel's location headers (free), and word it as "approximate area". | P2 |
| B16 | **ADR 0011 names `packages/ui-tokens`**, but the repo and tech design say `packages/tokens`. | A small inconsistency. | Fix the ADR. | P0 |

## C. Security, privacy and safety

| ID | Finding | Fix | When |
|---|---|---|---|
| C1 | **No threat model.** | A one-page model covering code guessing, finder impersonation at handover, phishing through owner messages, fake tags that copy Tagkin's look ("quishing"), stalking by tag, scraping. Each threat mapped to a control. | P1 |
| C2 | **Links in owner finder messages** aren't blocked. | Block URLs in finder messages and labels; never turn text into links on finder pages. | P2 |
| C3 | **Photo moderation.** Owner photos are public on finder pages; Apple guideline 1.2 asks for content filtering. | Automated image check at upload (an EU-hosted service, or a moderation queue for anything flagged) and a report path. | P2 |
| C4 | **Fake tags (quishing).** Lookalike stickers can point to phishing sites. | The finder page always shows tagkin.app plainly, never asks for payment, and the help page explains it. | P2 |
| C5 | **Finders' data rights.** Finders have no account, but their email is stored. | A privacy notice on the finder page; a deletion request through the report link; a retention period for finder contacts. | P2 |
| C6 | **EU Digital Services Act (DSA) for user content.** | A single point of contact, notice and action (we have Report), a statement of reasons when content is removed, and moderation terms. Small companies are exempt from transparency reports only. | P2, X |
| C7 | **Account security of the business.** | A password manager, two-factor sign-in on GitHub, Cloudflare, Stripe, Supabase, Vercel, Apple and Google, and recovery codes stored offline. GitHub push protection and secret scanning in batch 2. | P0 |
| C8 | **Minimum age** for owners isn't set (GDPR consent age in Germany is 16; purchases). | Terms say 16+ to use and 18+ (or parental consent) to buy; the store age rating follows. | P2 |
| C9 | **Data protection impact assessment.** Location data, the photos and possibly children (later Care tags). | A short assessment and records of processing (already in Stage E), started with the legal texts. | P2 |

## D. Business, legal and operations

| ID | Finding | Where it hurts | Fix | When |
|---|---|---|---|---|
| D1 | **Legal entity:** sole trader (Einzelunternehmen) or a small limited company (UG). | Personal liability for products and data; the Apple account appears under your personal name. | Decide with a tax advisor. A UG limits liability and allows an Apple organisation account (needs a D-U-N-S number). | P2 |
| D2 | **Trade registration (Gewerbeanmeldung), tax number, small-business VAT scheme (Kleinunternehmerregelung) or VAT, and the EU One-Stop Shop (OSS)** for sales to other EU countries. | Stripe verification; correct prices "incl. VAT"; invoices. | Tax advisor before M2. | P3 |
| D3 | **Impressum address.** German law requires a postal address that can receive mail. | Your home address goes public. | A business address service, if allowed; decide with D1. | P2 |
| D4 | **Legal pages too late.** TK-80 and TK-81 are in M5, but M1 finder pages are public, and TK-20 links to pages that don't exist yet. | Warning letters and broken links. | Move the Impressum, privacy notice (incl. finder data) and terms of use to **M1**; the terms of sale, withdrawal information and returns to **M2**. | P2 |
| D5 | **EU product safety regulation (GPSR):** manufacturer and responsible person, product ID and safety warnings on each product page; traceability on the product or packaging. | Listings can be taken down; fines. | Partner documentation; GPSR block on product pages; batch or order ID on the packaging. | P3 |
| D6 | **German packaging law, LUCID registration:** sellers must register even when a print-on-demand partner ships (the rules changed in 2026). | Sales ban for unregistered sellers. | Register with LUCID before the first sale; confirm the current law with the advisor. | P3 |
| D7 | **Insurance:** business and product liability. | A defective pet tag or a data incident. | Quote with D1. | P3 |
| D8 | **Trademark filing sits in Stage E**, but the name goes public with M1 and Community publishing. | Someone files "Tagkin" first. | File the EU trademark (classes 9, 16, 26 and 42 to check) before the web beta, ideally before the Community publish. | P2 |
| D9 | **Name squatting.** | Others take @tagkin and the app store names. | Reserve social handles now; reserve the App Store name when the developer account exists. | P2 |
| D10 | **Costs of the free tiers.** Vercel Hobby is non-commercial; Supabase backups and point-in-time recovery are paid; EAS has build limits. | Terms breach or data loss. | Vercel Pro before public M1; Supabase Pro before real users; a monthly cost sheet with alerts. | P1 |
| D11 | **No admin or support tooling until M5** (TK-90), but refunds, reprints, address fixes and moderation start in M2. | Manual SQL in production. | A minimal admin in M2 (orders, refunds, reprint, address, reports) and written runbooks. | P3 |
| D12 | **No ordering kill switch.** | A partner outage keeps taking paid orders. | Feature flags (PostHog) for ordering, gifting and translation. | P3 |
| D13 | **The German checkout-button rule.** The pay button must say clearly that the order costs money. | Orders that aren't binding. | Lawyer check of "Pay €x with …" or use "Buy now · €x". | P3 |
| D14 | **Invoices.** German invoice rules (numbering, VAT or small-business note). | Missing or wrong invoices. | Stripe invoices with the right fields, or our own PDF. | P3 |

## H. Ideas worth noting (P5)

- **Owner web push or installable web app** before the native apps exist, so M1 and M2 owners get instant alerts, not only email.
- **Apple Wallet or Google Wallet pass** as an extra digital "ID card" for the phone, next to the lock-screen tag.
- **NFC** on printed tags later (tap or scan).
- **Warranty and receipt vault** (an existing Premium idea): useful when a lost item needs to be proven as yours.
- **Lost-and-found desk partner view** (marketing point 4): staff look up a code and see "desk handover" options.
